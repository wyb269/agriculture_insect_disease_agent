# 神农卫田病虫害防治智能体产品升级 PRD

版本 V2.4

日期 2026年10月8日

适用范围 PC Web 微信小程序与移动 App 双端产品

## 一 文档目的

本文件用于指导神农卫田病虫害防治智能体从单次图片问答工具升级为可销售、可交付、可持续运营的病虫害防治产品。文档面向产品、设计、研发、算法、测试、运营、农业审核和项目交付团队，统一说明产品定位、跨端架构、界面设计、普通软件能力、大模型能力、安全边界、路线和验收标准。

本版根据 PC 端和移动端评审意见收敛产品范围。主要决策如下：

1. PC 和移动端使用同一套病虫害诊断、方案、执行和复查逻辑，只针对屏幕、输入设备和使用环境做交互适配。
2. PC 端不是独立客户管理平台。它保留完整诊断流程，并增加现有病害识别数据分析、批量查看和大屏操作效率能力。
3. 首期删除风险地图、区域治理、防控任务下发、多租户管理和客户验收报表，不为尚未确认的机构管理场景增加复杂度。
4. 用户问题必须在本产品内形成可执行结果。低置信病例不得转交农技人员、外部专家或其他人工诊断服务。
5. 当前智能诊断能力统一调用中国农业大学神农大模型 API，不自研或微调基础模型；这只限定模型能力来源，不削减正常产品需求。
6. 当前研发范围不建设知识库、向量库、文档解析、语义检索或 RAG。安全用药等确定性约束由经过审核的版本化安全规则配置包承担。
7. UI、病例、复查、数据分析和安全规则能力必须与模型优化解耦，可在当前模型不变时独立上线。
8. PC与移动端使用统一用户意图体系。意图识别采用页面事件、状态机、确定性规则和神农API的混合方案，不建设知识库，也不要求模型微调后才能上线。

## 二 产品定位与范围

### 2.1 产品方向

产品当前面向直接使用病虫害诊断服务的个人用户和一线种植人员。PC 与移动端不是两套业务系统，而是同一产品在桌面和田间两种环境中的入口。

两端共同解决以下问题：

1. 用户发现作物异常后，完成图片和症状采集。
2. 系统给出分层诊断结果和当前可执行措施。
3. 用户记录处理结果，并按提醒完成复查。
4. 用户可在任一端查看同一病例、历史记录和个人病害识别数据分析。

### 2.2 目标用户

| 用户 | 核心任务 | 主要使用环境 | 推荐端 |
|---|---|---|---|
| 普通种植户 | 拍照诊断 查看方案 记录处理 复查 | 田间和日常查看 | 移动端为主 PC为辅 |
| 家庭农场主 | 管理多次诊断 查看历史和变化 | 田间与办公室 | PC与移动端 |
| 园艺爱好者 | 识别家庭种植问题 获取易懂措施 | 家庭和庭院 | 移动端为主 |
| 基层农业从业者 | 快速识别 整理病例 查看识别数据 | 现场与办公桌面 | PC与移动端 |

### 2.3 产品目标函数

用户价值可表达为：

用户价值 = 判断可信度 × 行动可执行性 × 复查连续性 ÷ 操作成本

双端价值可表达为：

双端价值 = 业务一致性 × 数据同步完整度 × 场景适配度

产品设计应优先提高行动可执行性和数据闭环。PC 与移动端可以有不同布局，但不得形成两套诊断规则、数据口径或结果解释。

### 2.4 产品内解决的定义

一次病例满足以下四项才算产品闭环完成：

1. 系统给出明确的结果层级。
2. 系统给出当前可执行的措施。
3. 用户能够记录实际执行情况。
4. 系统给出复查时间和下一判断条件。

结果层级分为三类：

| 层级 | 适用条件 | 产品输出 |
|---|---|---|
| L1 病害级方案 | 证据足以支持具体病虫害 | 病虫害结论 针对性措施 复查标准 |
| L2 候选组方案 | 两个或多个候选暂时不能区分 | 候选对比 共同安全措施 区分观察项 复查时间 |
| L3 症状风险方案 | 图片或信息不足以确认病名 | 症状分类 风险控制措施 取证要求 复查和升级条件 |

L2和L3不是失败状态。它们必须交付用户当前能做的事情，并在产品内继续收集证据和重新计算。界面不得出现“转专家”“咨询农技员”“等待人工诊断”或同义入口。

### 2.5 产品边界

产品提供病虫害识别、危害程度判断、差异诊断、方案生成、执行记录、复查管理、历史查询和识别数据分析。产品不承诺每次都输出唯一病名，也不允许为了完成率而强行输出高置信结论。

涉及农药登记对象、剂量、使用次数、安全间隔期、禁限用和天气条件的内容必须通过经过审核的安全规则配置包和确定性程序校验。神农大模型只负责智能识别、比较、解释和方案草拟，不得凭生成文本直接决定药剂信息。

对于疑似检疫性有害生物或其他法定报告事项，产品展示明确的合规提示和用户应采取的临时控制措施。该提示不构成低置信诊断的人工兜底。

### 2.6 升级目标

1. 农户首次进入后10秒内找到拍照诊断入口。
2. 大多数用户在2分钟内完成一次有效取证和信息补充。
3. 每个有效病例都生成L1、L2或L3结果，不出现只有“无法识别”的死路。
4. 每个结果都包含行动、执行记录和复查计划。
5. PC端能够完成与移动端一致的诊断闭环，并查看个人或授权账号范围内的病害识别数据分析。
6. UI和普通功能在不微调、不更换模型时仍能按计划上线。
7. 用户的复合诉求被拆分为主意图和次意图并连续完成，不要求重复提问。
8. 意图低置信通过按钮澄清，诊断低置信通过L2或L3方案解决，两类问题不混淆。

## 三 跨端产品架构

### 3.1 端侧职责

| 维度 | PC Web | 微信小程序或移动 App |
|---|---|---|
| 服务逻辑 | 诊断 方案 执行 复查 历史 分析 | 诊断 方案 执行 复查 历史 分析 |
| 主要场景 | 桌面上传 深度查看 历史对比 数据分析 | 田间拍摄 即时诊断 执行记录 复查 |
| 主要输入 | 拖拽上传 相册 文件选择 键盘和筛选 | 相机 相册 语音 位置和快捷选择 |
| 主要输出 | 分层结果 行动方案 病例详情 识别数据图表 | 一屏结果 行动清单 用量提示 复查提醒 |
| 交互特点 | 宽屏双栏 批量查看 更完整筛选 | 单栏流程 大触控目标 弱网友好 |
| 数据范围 | 与同一账号移动端一致 | 与同一账号PC端一致 |

### 3.2 统一业务闭环

统一闭环为：发现异常、有效取证、结构化补充、获得分层结果、执行措施、记录执行、复查效果、继续或结束。

用户可以在任一端创建病例，并在另一端继续查看、补充、执行或复查。业务状态和结果口径完全一致，差异只存在于输入方式和页面布局。

PC 的识别数据分析从同一套病例数据生成，不额外创建风险事件、区域任务或管理工作流。

### 3.3 统一业务对象

两端共用以下对象：用户、作物档案、可选地块、诊断病例、图片、症状信息、候选结果、结果层级、处理方案、行动记录、复查记录、安全规则包、方案模板、API调用记录和分析指标。

本版不设置专家服务单、人工诊断单或外部转交单。

### 3.4 差异化产品亮点

1. 三视图取证。用病斑近景、病部背面或侧面、全株或环境图提高信息质量。
2. 双置信度。分别展示诊断置信度和行动置信度，避免病名不确定就无法行动。
3. 分层解决。L1给具体方案，L2给候选共同方案，L3给症状风险方案。
4. 深度诊断。系统通过补拍、结构化追问、候选对比和复查继续收敛，不转交外部人员。
5. 行动优先。结果首屏先说明现在做什么，再解释模型看到了什么。
6. 识别数据分析。PC端用同一账户的病例生成作物、病虫害类别、时间趋势和复查结果统计。
7. 可追溯建议。具体措施绑定规则包版本、适用地区、适用条件、有效期和生成时间。
8. API隔离。当前生产模型固定为神农大模型 API，前端只消费统一结构，不感知鉴权方式、原始响应和接口变更。

### 3.5 模型解耦原则

需求按依赖等级划分：

| 等级 | 定义 | 典型能力 | 发布方式 |
|---|---|---|---|
| A0 无模型依赖 | 前后端 规则 数据接口可以完成 | UI 上传 病例 历史 复查 数据分析 权限 | 独立开发测试发布 |
| A1 弱模型依赖 | 使用神农大模型 API 当前已提供的结果 | 结果卡 候选展示 通俗解释 | 字段可缺失 可使用模拟数据验收 |
| A2 强模型依赖 | 依赖神农大模型 API 新增字段或能力 | 多图融合 病斑定位 智能追问 变化比较 | 单独联调灰度 可随时关闭 |

产品路线分为产品工程线和神农 API 能力增强线。产品工程线不等待 API 能力增强完成。任何A2能力关闭时，用户仍能在两端完成建档、上传、结构化问诊、基础分层方案、执行记录、复查和历史分析。A2是正常目标需求，只是独立排期和验收，不因当前接口不足而从产品范围删除。

### 3.6 用户意图在产品中的作用

用户意图表示用户希望系统此刻完成的任务。作物、病虫害、病部、症状和药剂属于实体，不按数百个病虫害名称扩展意图类别。同一套意图体系服务PC和移动端，端侧只调整输入控件和展示形式。

用户常见表述及产品目标如下：

| 用户表述 | 直接诉求 | 实际决策 | 产品输出 |
|---|---|---|---|
| 这是什么病 | 识别病名 | 是否需要立即处理 | 分层结论 依据 立即行动 |
| 怎么治 | 获取方案 | 如何控制损失 | 综合防治步骤 优先级 复查条件 |
| 打什么药 | 选择药剂 | 如何安全有效施用 | 对象确认 标签校验 用法和安全限制 |
| 严不严重 | 判断危害 | 是否投入时间和成本 | 严重度 扩散风险 行动紧迫度 |
| 为什么不确定 | 理解结果 | 是否相信系统及如何继续 | 候选差异 缺失证据 共同措施 |
| 处理后还是这样 | 复查效果 | 继续 调整或结束 | 前后比较 效果结论 下一行动 |

产品优化目标可表示为：

有效解决率 = 正确理解任务 × 有效取证 × 可执行方案 × 安全校验 × 复查闭环

### 3.7 五维意图模型

每轮用户请求解析为主意图、次意图集合、会话阶段、槽位状态和风险标签。

| 维度 | 含义 | 示例 |
|---|---|---|
| 主意图 | 本轮必须首先解决的任务 | 图片诊断 |
| 次意图 | 同时提出但依赖主任务的诉求 | 严重程度 药剂选择 |
| 会话阶段 | 病例当前所处流程 | 待取证 诊断中 待复查 |
| 槽位 | 完成任务所需的变量 | 作物 病部 地区 面积 |
| 风险标签 | 需要强制安全约束的事项 | 具体用药 人畜暴露 疑似检疫 |

示例输入“番茄叶子有斑，是什么病，怎么治，打什么药”应识别为一个诊断主意图、综合防治和药剂选择两个次意图。系统先补齐诊断所需证据，再生成方案，最后执行药剂安全校验。用户不需要重复提问。

| 编码 | 意图域 | 用户目标 | 产品路由 |

| SYS | 会话与导航 | 开始 了解能力 重置或确认选择 | 首页 帮助 流程控制 |
| DIA | 诊断与识别 | 判断作物 病虫害或异常原因 | 诊断编排 |
| EVI | 补充与纠正证据 | 提供信息 补拍或纠错 | 槽位填充 证据管理 |
| RES | 结果理解 | 理解证据 置信度 严重程度和差异 | 结果解释 候选对比 |
| CTL | 防治与预防 | 获得当前可执行的综合措施 | 行动方案 |
| PES | 用药与安全 | 选择并安全使用农药 | 标签规则校验 计算器 |
| REV | 执行与复查 | 记录措施 判断效果和下一步 | 行动记录 复查流程 |
| DAT | 病例与数据 | 查询 继续 管理病例和个人统计 | 历史 搜索 数据分析 |
| SRV | 产品与服务 | 查询覆盖 账号 权益 隐私和故障 | 产品帮助 |

完整二级标签库包含79项语义标签，见附录一。79项标签用于统一语言、日志和评测，不要求首期把每项都实现为独立模型分类器。页面事件、状态和确定性规则可以直接识别的意图，不进入模型分类。

### 3.9 主次意图和任务依赖

复合诉求按最早未满足的依赖选择主意图。依赖顺序为：诊断、方案、用药校验、执行记录、复查。

系统输出一个主意图和最多三个次意图。次意图进入当前病例的待处理队列，在依赖满足后继续执行。结果页应明确展示已经完成、正在处理和等待条件的诉求，不能只回答第一句或要求用户重新输入。

### 3.10 意图置信度和诊断置信度

| 类型 | 含义 | 低置信处理 |
|---|---|---|
| 意图置信度 | 系统是否理解用户要完成的任务 | 提供2至3个互斥任务按钮澄清 |
| 诊断置信度 | 系统能否确定病虫害结论 | 输出L2候选组或L3症状风险方案 |

两种置信度分别计算、展示和记录。意图低置信不能显示为病虫害识别失败；诊断低置信不能触发人工转单。

### 3.11 槽位体系和追问规则

| 槽位组 | 核心字段 | 主要来源 |
|---|---|---|
| 病例 | 病例编号 状态 创建时间 | 系统上下文 |
| 作物 | 作物 品种 生育期 株龄 | 用户 图片 档案 |
| 病部症状 | 病部 颜色 形态 病征 分布 | 用户 图片 |
| 发生发展 | 起始时间 持续时间 扩散速度 受害比例 | 用户 历史 |
| 环境 | 地区 设施类型 天气 温湿度 | 用户 授权天气 |
| 农事历史 | 灌溉 施肥 用药 前茬 | 用户 行动记录 |
| 图片 | 图片编号 视角 质量 拍摄时间 | 上传和图片质检 |
| 用药安全 | 产品 有效成分 登记证号 采收期 次数 | 用户 安全规则配置包 |
| 计算 | 面积 水量 标签剂量 稀释倍数 单位 | 用户 确定性计算器 |
| 偏好 | 绿色防控偏好 可用工具 紧迫度 | 用户 |

每个槽位保存原始值、规范值、来源、置信度、状态和更新时间。用户确认值优先于模型推断值，纠错后保留修订记录。每轮最多询问两个高信息增益问题，并允许用户选择“不清楚”。已标记未知的字段不得在同一阶段循环追问。

### 3.12 会话状态和上下文

意图会话状态为：空闲、信息收集、诊断中、结果已生成、方案已形成、措施已记录、待复查、已复查和已结束。

状态机由普通程序维护。模型可以返回内容和建议的下一动作，但不能直接修改病例状态。补证、纠错和重新诊断可回到信息收集或诊断状态，旧结果必须保留版本。

否定、指代和省略必须结合上下文解析。“不要用药”表示绿色偏好，不是药剂选择；“不是番茄”触发作物槽位纠错；“上次那个”和“第一个”必须引用明确候选；在待复查状态说“还是很多”优先进入无效或加重流程。

### 3.13 混合识别和模型解耦

意图识别依次使用页面事件、会话状态、确定性规则和神农大模型API。页面按钮、拍照、设置复查和删除病例等明确事件直接路由。面积、体积、单位、用量、稀释、混配、人畜暴露和危险用药先由高精度规则识别。其余自由文本由神农API输出受约束的主次意图和槽位候选。

融合逻辑可表示为：

意图得分 = 模型得分 + 规则得分 + 上下文得分 + 页面事件得分 - 冲突惩罚

各项权重和阈值通过真实脱敏日志校准，PRD不预设未经验证的数值。规则和模型冲突时，安全标签优先，业务状态其次，模型评分最后。神农API不可用时，按钮、状态机、表单、高风险规则和病例流程继续运行。

### 3.14 跨端意图交互

PC与移动端使用相同标签、槽位、状态和结构化协议。移动端提高拍照、语音和快捷按钮权重，澄清使用大触控选项；PC提高键盘长文本、历史上下文和并列证据权重，支持候选与槽位在同屏确认。跨端继续病例时必须恢复同一意图队列和已确认槽位。

### 3.15 意图结构化协议

意图服务返回协议版本、主意图、最多三个次意图、会话阶段、槽位、缺失槽位、风险标签、下一动作、产品路由、候选意图和追踪编号。模型缺失字段保持缺失，前端不得猜测补齐。

意图结果属于诊断请求的上游编排字段。它决定页面和服务路由，不替代神农API的病虫害诊断结果，也不允许修改安全规则校验结论。

### 3.16 意图专项指标

| 指标 | 定义 | 用途 |
|---|---|---|
| 主意图准确率 | 主意图预测正确的轮次比例 | 衡量总体路由 |
| Macro F1 | 各意图F1的算术平均 | 防止高频类别掩盖小类错误 |
| Top 2召回率 | 正确意图是否位于前两名 | 衡量澄清选项质量 |
| 多意图召回率 | 次意图被识别的比例 | 衡量复合诉求完整性 |
| 槽位F1 | 槽位边界和值的综合正确性 | 衡量结构化抽取 |
| 高风险意图召回率 | 用药 暴露 检疫和危险请求的召回率 | 安全门槛 |
| 错路由率 | 进入错误产品流程的轮次比例 | 衡量业务损失 |
| 澄清成功率 | 一次澄清后正确路由的比例 | 衡量兜底效果 |
| 无匹配率 | 进入无匹配澄清的比例 | 发现覆盖缺口 |

首版没有真实日志，不写死统一准确率。发布门槛按诊断、方案、用药和复查四条关键路由分别评测，高风险漏识别逐例复盘。

## 四 PC Web 产品设计

### 4.1 信息架构

一级导航设置为：首页、拍照诊断、诊断记录、数据分析、作物档案、我的。

PC端不再设置区域总览、风险地图、防控任务、组织管理和客户验收报告。首页突出“上传图片开始诊断”和最近病例，不将通用聊天框作为核心入口。

### 4.2 诊断流程

1. 用户可拖拽或选择一至多张图片，并按病斑近景、病部背面或侧面、全株或环境调整顺序。
2. 图片上传后进入与移动端一致的结构化问诊，字段、必填规则和默认值完全相同。
3. 结果页使用宽屏双栏。左侧展示图片、证据和候选，右侧展示L1至L3结果、行动清单和复查计划。
4. 用户可以记录已执行措施、上传复查图片并结束病例，状态与移动端实时同步。
5. L2和L3病例突出缺失证据和当前可执行措施，不显示外部转交入口。

### 4.3 诊断记录

1. 提供列表和缩略图两种视图，不提供地图视图。
2. 支持按作物、病虫害候选、结果层级、时间、执行状态和复查状态筛选。
3. 病例详情展示图片、症状、模型结果、行动记录和复查时间线。
4. 支持收藏、添加个人备注和导出单个病例摘要，不支持批量修改诊断结论。
5. 从PC打开移动端创建的病例时，直接进入同一病例编号和最新状态。

### 4.4 病害识别数据分析

数据分析只基于用户本人或当前账号已授权查看的诊断记录，不引入区域风险推断。首期保留以下现有分析能力并统一口径：

1. 诊断次数、有效病例数、结果层级分布和复查完成率。
2. 作物分布、病虫害类别分布及其明细病例。
3. 按日、周、月查看诊断数量和主要类别变化。
4. 查看已执行措施、改善、稳定、加重和无法比较的数量。
5. 图表均可点击回到组成病例，统计值与列表筛选结果一致。

首期不提供风险地图、空间热点、疫情预测或自动预警。这些能力需要稳定的位置授权、足够样本、气象数据、风险阈值和隐私治理，不能由现有识别记录直接推出。

### 4.5 双端连续使用

1. PC与移动端使用同一账号体系、病例编号和数据权限。
2. 任一端新增图片、修改问诊信息、记录执行或完成复查后，另一端刷新即可看到最新状态。
3. 移动端适合现场采集，PC适合补充长文本、对比多张图片、查看历史和分析数据。
4. 同一病例不得在两端形成两个互不关联的结果版本；重新诊断必须生成可追溯的新版本。

### 4.6 PC 视觉与交互规范

1. 使用农业绿作为品牌主色，深蓝用于信息和证据，橙色用于提醒，红色仅用于高风险。
2. 页面背景采用低饱和浅灰，内容区使用白色，避免大面积渐变、发光阴影和满屏装饰图。
3. 正文最小14像素，表格最小13像素，行高不低于1.5。
4. 采用8像素间距基准，主要卡片圆角12像素，按钮圆角8至10像素。
5. 数据分析页面只保留关键指标、趋势和分布图，不堆叠无操作价值的小卡片。
6. 所有图表提供文本摘要和数据明细入口，筛选与表格支持键盘操作和清晰焦点状态。
7. 空状态明确说明缺少什么数据以及下一步操作，不展示虚构示例值。

### 4.7 PC 端不依赖大模型的功能

| 功能 | 需求说明 | 验收标准 |
|---|---|---|
| 图片上传 | 拖拽 选择 多图排序 删除和补传 | 不进入聊天页即可开始诊断 |
| 结构化问诊 | 与移动端使用相同字段和校验规则 | 同一输入在两端形成同一请求结构 |
| 诊断记录 | 检索 筛选 收藏 备注和单病例导出 | 筛选结果与明细一致 |
| 病例时间线 | 展示诊断 执行 复查和版本变化 | 关键变更包含时间和来源端 |
| 作物档案 | 管理作物 品种 生育期和可选地块 | 两端编辑后数据一致 |
| 数据分析 | 统计数量 类别 趋势 结果层级和复查效果 | 图表可下钻且统计口径可见 |
| 执行与复查 | 记录措施 用量 时间 图片和复查结论 | 与移动端状态实时一致 |
| 数据导出 | 导出本人单病例摘要和授权数据 | 默认不包含精确位置和敏感信息 |

### 4.8 PC 端需要大模型的功能

1. 完成与移动端一致的作物、病部、症状和病虫害识别。
2. 融合多图和结构化问诊生成L1、L2或L3结果。
3. 解释支持证据、冲突证据和相似候选差异。
4. 将单病例证据、执行记录和复查结果整理为可读摘要。
5. 对个人识别数据生成文字概览，但所有数字必须来自确定性统计。

这些能力关闭时，诊断记录、确定性数据分析、执行记录和复查仍可正常使用。

### 4.9 内部运维后台边界

首期不建设面向客户的独立管理端。研发仍需提供轻量内部运维后台，用于神农API配置、接口状态监控、安全规则配置包发布、用户状态查询、问题定位和审计日志。该后台不提供区域地图、机构任务下发、经营报表或客户自助组织管理，也不作为对外售卖模块。

### 4.10 PC意图交互

PC诊断页在图片区、文字输入区和结果区之间保持同一意图上下文。用户输入复合诉求时，右侧显示主任务和待处理诉求，不使用通用聊天消息流掩盖诊断流程。意图低置信时在输入区下方显示最多三个澄清按钮；已有病例上下文时，按钮优先使用“重新诊断”“查看方案”“复查结果”等业务动作。

## 五 移动端产品设计

### 5.1 信息架构

底部导航设置为：首页、诊断、记录、我的。诊断按钮可以突出，但不得遮挡页面内容。

首页顺序为：拍照诊断、待复查病例、最近病例、常用作物。现有大段品牌介绍和推荐问答移到产品介绍与帮助页。

### 5.2 首页

1. 主按钮使用“拍照诊断”，次按钮使用“从相册选择”。
2. 首次使用展示病斑近景、病部背面或侧面、全株或环境三张拍摄示例。
3. 待复查区域显示到期病例和继续诊断入口，不混入管理任务或营销内容。
4. 最近病例显示缩略图、作物、结果层级、主要判断和复查时间。
5. 我的页面提供简化版个人数据分析，并可跳转PC查看完整图表。

### 5.3 拍摄与信息补充

1. 相机取景框显示距离、光线和拍摄部位提示。
2. 拍完一张后说明还缺少哪一种视角。
3. 图片模糊、过暗、主体过小或重复时立即提示重拍。
4. 用户可以跳过部分图片，但系统必须说明这会影响哪个判断。
5. 信息补充使用单选、多选和快捷标签，每屏只解决一个主要问题。
6. 语音描述必须实时转成文字并允许修改。
7. 已从图片或档案推断的信息必须让用户确认，不能直接当作事实。

### 5.4 结果页

结果页第一屏包含：主要判断、结果层级、诊断置信度、行动置信度、风险等级和“现在做什么”。

向下依次展示：

1. 识别依据和相似候选。
2. 今日行动清单。
3. 未来三天观察项。
4. 复查时间和复拍示例。
5. 农药安全卡或绿色防控卡。
6. 方案适用地区、安全规则版本和生成时间。

底部固定动作设置为“记录执行”“设置复查”“继续诊断”。不得设置咨询、转交或等待人工处理按钮。

### 5.5 深度诊断模式

L2或L3结果进入产品内深度诊断模式：

1. 系统先显示当前可立即执行的保守措施。
2. 每轮最多提出两个最能区分候选的问题。
3. 提供对应视角的补拍引导。
4. 展示候选差异，允许用户选择看到或未看到的症状。
5. 达到停止条件后重新计算L1、L2或L3结果。
6. 仍不能确定病名时，输出完整症状风险方案和24至72小时复查计划。

整个流程不离开产品，不创建外部服务单。

### 5.6 执行与复查

1. 用户按行动清单勾选完成情况，并记录时间、用量、天气和照片。
2. 化学防治填写面积和药剂后，由确定性计算器计算用量范围。
3. 复查时按照首次拍摄角度提供轮廓提示，减少图片不可比。
4. 系统输出改善、稳定、加重或无法比较，并给出下一行动。
5. 症状消失或达到观察周期后，用户确认结束病例。

### 5.7 移动端视觉规范

1. 单栏布局，主要内容在一屏内形成明确阅读顺序。
2. 主要触控目标不小于44乘44逻辑像素，按钮间距不小于8像素。
3. 首屏只保留一个主行动，不让聊天输入框与拍照入口竞争。
4. 结果等级同时使用文字、图标和颜色，不仅依赖颜色。
5. 农药安全信息使用独立版式，关键单位加粗，禁止与广告混排。
6. 底部区域适配安全区和键盘，固定按钮不遮挡最后一项内容。
7. 纯图标按钮具备读屏名称，隐藏面板关闭后不进入焦点顺序。
8. 弱网和加载状态显示已保存内容、剩余步骤和可恢复操作。

### 5.8 移动端不依赖大模型的功能

| 功能 | 需求说明 | 验收标准 |
|---|---|---|
| 拍照与相册 | 独立入口 支持多图 补拍 排序 删除 | 不经过隐藏菜单即可使用 |
| 拍摄教程 | 正确错误示例 距离 光线 部位 | 首次可跳过 随时可重看 |
| 本地质量检查 | 分辨率 模糊 曝光 体积 网络 | 无效图片上传前提示 |
| 弱网续传 | 压缩 断点续传 失败重试 草稿 | 网络恢复后继续原病例 |
| 结构化问诊 | 作物 部位 时间 范围 环境快捷选择 | 不输入长文本也能完成 |
| 行动清单 | 措施 时间 材料和完成状态 | 每项可记录与撤销 |
| 用量计算器 | 面积 稀释倍数 单位换算和上限提示 | 计算过程可复核 |
| 复查提醒 | 定时提醒 复拍角度和观察项目 | 用户可关闭或改期 |

| 天气窗口 | 显示降雨 风速 温度等规则条件 | 无定位时可手选地区 |
| 个人数据概览 | 显示诊断量 作物 病虫害类别和复查状态 | 与PC统计口径一致 |
| 隐私设置 | 相机 相册 位置 通知和数据用途 | 权限拒绝后说明降级方式 |

### 5.9 移动端需要大模型的功能

1. 识别作物、病部、症状和危害程度。
2. 识别照片视角并判断缺少的证据。
3. 融合多图和结构化信息生成候选结果。
4. 根据候选差异生成最短追问路径。
5. 解释关键症状和相似病害区别。
6. 将神农 API 诊断结果与已审核方案模板组织为分层行动方案。
7. 总结复查变化并提出下一行动。
8. 从语音描述提取字段，提取结果仍需用户确认。

### 5.10 移动端意图交互

移动端优先通过拍照、结果页动作和复查入口确定意图。语音或文本出现多个诉求时，先展示当前主任务，并在结果页连续完成严重程度、方案和安全用药等次意图。澄清选项使用大按钮，不要求用户重新组织句子。底部输入框只用于补充描述，不能取代拍照诊断、记录执行和复查等主入口。

## 六 不依赖大模型的核心功能

### 6.1 账号与双端同步

移动端支持微信授权和其他低门槛登录，PC端支持同一账号登录或扫码登录。两端使用同一用户标识、病例编号、作物档案、行动记录和复查状态。用户拒绝定位后仍可手动选择地区，不影响基础诊断流程。

### 6.2 作物 地块与种植档案

作物档案包含作物、品种、种植方式、生育期、所在地、规模和备注。地块档案为可选功能，包含名称、面积和可选位置，不要求归属组织或行政管理关系。首次使用仅要求作物，其他信息逐步补充。

### 6.3 病例状态机

病例状态设置为：草稿、待补充、诊断中、已生成方案、执行中、待复查、复查中、已结束。

状态由确定性规则维护。任何状态都不指向外部人工服务。模型只返回内容字段，不能直接修改病例状态。

### 6.4 安全规则配置包与校验引擎

当前版本不建设知识库、向量库、文档解析管道、语义检索或 RAG。研发只实现结构固定、可版本化的安全规则配置包，字段至少包含配置来源说明、发布日期、有效期、适用地区、作物、病虫害对象、审核状态和版本号。校验引擎负责农药登记对象、禁限用、剂量范围、使用次数、安全间隔期、防护、天气限制和单位换算。

配置包由业务、农业审核和合规人员在线下审定后，以约定格式导入；系统仅提供导入校验、发布、撤回、版本查看和回滚，不承担知识生产。配置包不可用、过期或未命中时，系统仍可给出非化学低风险措施、观察项和复查计划，但禁止展示具体药剂、剂量、混配和安全间隔期。

### 6.5 方案模板与行动记录

方案由固定行动模板、安全规则校验结果和神农 API 解释共同组装。每项行动包含目的、方法、完成条件、预计时间、所需材料、风险和复查点。用户可以记录完成、跳过和跳过原因。

### 6.6 个人识别数据统计

系统按用户可访问的病例范围，使用确定性查询统计诊断数量、作物、病虫害类别、结果层级、执行状态和复查结果。统计不使用大模型，不生成空间热点、区域风险等级或疫情预测。每个汇总指标都能下钻到组成病例。

### 6.7 通知与复查提醒

通知类型包括补充信息、行动到期、复查到期、诊断完成和服务状态。每类通知可独立关闭。通知只与用户自己的病例和服务状态相关，不发送区域风险或客户管理任务。

### 6.8 数据 权限与安全

图片、语音和位置按最小必要原则采集。精确位置默认不进入数据分析、导出和分享。用户可以查看、下载和删除个人数据。训练或评测使用必须单独告知并允许退出。

测试环境只使用脱敏或合成数据。日志不得记录明文手机号、精确地块坐标、未脱敏图片地址和访问凭证。

### 6.9 异常与降级

必须覆盖无网络、弱网、上传失败、图片无效、神农 API 超时、神农 API 不可用、安全规则配置包不可用、定位拒绝、通知关闭和服务维护。

异常处理原则是保存用户已完成的工作并提供下一步。不得用缓存结果冒充本次诊断，也不得把“联系某人”作为系统失败后的产品路径。

### 6.10 服务交付

首期产品按统一在线服务交付，覆盖PC Web、微信小程序和移动App。不同渠道可以配置账号权益、诊断次数和存储期限，但不得形成不同的诊断逻辑或结果标准。

具体价格、权益来源和调用配额在商务方案中维护。首期不把区域SaaS、客户私有化部署、一体机和独立管理端作为产品必选能力，也不设计面向用户的人工复核付费项目。

### 6.11 意图路由服务

普通程序维护意图标签版本、页面事件映射、会话状态、主次意图依赖、槽位状态、风险标签、澄清选项和脱敏埋点。意图路由服务允许研发使用模拟结果独立验收，不等待神农API新增能力。

高风险规则必须覆盖具体用药、剂量、稀释、混配、安全间隔期、人畜暴露、疑似检疫和绕过安全规则的请求。命中后先执行确定性安全逻辑，再决定是否调用神农API生成解释文本。

## 七 产品内诊断与解决引擎

### 7.1 双置信度模型

系统分别计算诊断置信度和行动置信度。

诊断置信度表示具体病虫害名称的可信程度，优先使用神农 API 明确返回并经过验证的置信字段；若 API 未提供，则显示“暂未提供”，不得从措辞、排序或文本中伪造概率。行动置信度表示当前措施在已知条件下是否安全、适用和可执行，由本产品确定性计算。

行动置信度由配置有效性、规则完整性、场景适配性和证据覆盖共同约束，可采用最小值原则：

行动置信度 = min 配置有效度 规则完整度 场景适配度 证据覆盖度

因此，具体病名尚未确定时，系统仍可以给出候选共同适用的高行动置信度措施。

### 7.2 结果层级决策

1. 当诊断证据充分且规则可用时输出L1。
2. 当候选难以区分但共同措施安全时输出L2。
3. 当病名证据不足时输出L3，重点控制扩散、改善环境、保存样本和安排复查。
4. 当图片不可用时先完成补拍步骤。用户暂时无法补拍时保存L3临时方案和待补充状态。
5. 任一层级都必须包含现在做什么、何时复查和什么条件下调整方案。

### 7.3 深度诊断停止条件

深度诊断最多三轮，每轮最多两个问题。出现以下任一条件时停止追问并生成新方案：

1. 已达到L1所需证据。
2. 新问题的信息增益低于阈值。
3. 用户连续两轮选择不确定。
4. 达到三轮上限。
5. 当前行动方案已足够安全，不需要为行动继续追问。

停止追问后不得显示死路。系统必须输出L1、L2或L3方案。

### 7.4 产品层解决验收

产品层解决不等于每次都预测正确病名。验收重点是：

1. 有效病例的方案可用率达到100%。
2. 低诊断置信病例仍有高行动置信度的保守措施。
3. 用户知道该做什么、为何这样做、何时复查和如何判断变化。
4. 复查后系统能继续、调整或结束方案。
5. 主流程没有外部人工诊断依赖。

## 八 大模型能力总体设计

### 8.1 模型与普通程序的边界

神农大模型 API 负责理解图片和自然语言、生成候选、选择追问、比较证据、解释结论和总结变化。普通程序负责账号、上传、权限、病例状态、数据统计、通知、行动记录、单位换算、安全规则版本、药剂校验、导出和数据删除。

任何数值统计和合规校验均由确定性程序完成。神农 API 返回内容必须经过结构解析和安全规则校验后才能进入结果页。调用模型 API 是智能能力实现方式，不改变 PC 与移动端正常业务需求及验收范围。

### 8.2 神农大模型 API 接入架构

PC和移动端不得直连神农大模型 API，前端只访问本产品诊断服务层。调用链为：PC或移动端、业务后端、诊断编排服务、神农 API 适配器、中国农业大学神农大模型 API。业务后端同时调用病例服务、安全规则校验引擎、解决引擎和结果组装器，全链路不包含自建知识检索服务。

神农 API 适配器负责服务端鉴权、请求组装、图片传输、超时、有限重试、熔断、限流、追踪编号、响应解析和错误映射。API 密钥只存放在服务端密钥管理或受控配置中，不得下发客户端、写入普通日志或进入导出文件。统一诊断协议允许字段为空；适配器只能映射 API 实际返回内容，不能补造候选、置信度、证据或模型版本。神农 API 后续增加病斑、证据、多图或复诊能力时，客户端主流程保持不变。

当前生产模型固定为神农大模型 API。此处的“解耦”用于隔离接口变化、故障和字段差异，不代表首期建设多模型路由，也不以替换模型为产品卖点。

| 接入项 | 产品要求 | 验收方式 |
|---|---|---|
| 鉴权 | API凭证仅保存在服务端受控配置或密钥管理中 | 客户端包 抓包 普通日志和导出文件均无凭证 |
| 请求组装 | 按神农API正式规范传输图片与结构化字段 | 使用官方样例和边界样例联调通过 |
| 图片处理 | 上传前校验格式 体积 方向和可用性 不擅自降低诊断所需清晰度 | 原图与处理图可追踪 失败有明确原因 |
| 超时 | 连接和整体响应分别设置超时 具体阈值以联调基线确定 | 模拟超时后病例不丢失且进入可恢复状态 |
| 重试 | 只对网络瞬断和明确可重试错误有限重试 | 同一病例不产生重复结果或重复计费记录 |
| 幂等 | 每次诊断使用唯一请求编号 重复提交可识别 | 重放同一请求不会生成两个病例结果 |
| 限流 | 按渠道 用户和接口配额保护服务 | 超限提示明确 不影响已保存病例和历史查询 |
| 熔断 | 连续异常达到阈值后暂缓新调用并进入降级 | 不形成请求风暴 恢复探测成功后自动解除 |
| 响应解析 | 只映射正式字段 保留未知和缺失状态 | 非法枚举 空字段和结构变化均有测试样例 |
| 安全校验 | 模型文本中的药剂与剂量必须再过确定性规则 | 绕过规则的具体用药信息无法进入发布结果 |
| 可观测性 | 记录追踪编号 耗时 状态码 字段完整率和调用量 | 可按时间 渠道和接口状态排查 不记录敏感正文 |
| 成本与配额 | 记录调用次数 成功率 重试量和可计量资源 | 统计与接口方账单可对账 异常增长可告警 |

### 8.3 API能力与产品需求的关系

产品需求按目标用户体验完整定义，不能因为神农 API 当前暂缺某字段而删除正常需求。接口现状与目标需求的差额形成“API能力缺口清单”，由产品、研发和中国农业大学接口方共同确认实现方式、交付时间和验收样例。

必须确认的接口项包括：支持的图片数量与格式、图文联合输入、会话上下文、候选数量、置信度字段、证据字段、病斑定位、响应结构、模型版本、限流配额、超时口径、错误码、数据留存和更新通知。未确认前不把推测字段写成已具备能力，但对应目标功能仍保留在A2路线中。

| 产品目标需求 | 所需神农API能力 | 当前文档状态 | 产品侧实现责任 |
|---|---|---|---|
| 单图病虫害诊断 | 图片加文字输入 诊断结论 | 以正式接口文档和联调为准 | 上传 编排 结果卡 病例保存 |
| 多图融合 | 单次多图或同病例上下文融合 | 待确认 A2 | 多图采集 排序 视角标签 展示 |
| L2候选组 | 多候选及排序或可区分信息 | 待确认 A2 | 候选对比 共同措施 继续诊断 |
| 双置信度 | API诊断置信字段 | 待确认 A2 | 行动置信度由本产品确定性计算 |
| 证据解释 | 支持证据 冲突证据或可见症状 | 待确认 A2 | 证据卡片 字段缺失状态 可访问展示 |
| 智能追问 | 多轮上下文或基于候选的追问 | 待确认 A2 | 问题控件 回答保存 轮次和停止条件 |
| 病斑定位 | 坐标 掩膜或热区 | 待确认 A2 | 标注层开关 原图对照和失败隐藏 |
| 连续复诊 | 首次与复查图文的比较输入 | 待确认 A2 | 时间线 复拍引导 变化结果和后续行动 |
| 个人数据概览 | 诊断记录摘要能力 | 待确认 A2 | 数字由确定性统计提供 模型只生成文字说明 |

上述表格描述的是接口依赖，不是功能删减清单。产品团队按完整需求设计交互和数据结构，研发用模拟协议并行开发；神农 API 能力经联调确认后再打开对应功能开关。

### 8.4 降级策略

1. 神农 API 超时：保存病例并进行有限后台重试，用户先查看基于固定模板的L3临时方案。
2. 神农 API 返回低置信：进入深度诊断，生成L2或L3方案，不转交外部人员。
3. 神农 API 不可用：保留结构化问诊、基础L3方案、行动记录和复查；恢复后用户可在原病例重新发起诊断。
4. 神农 API 响应结构异常：保存原始追踪编号，适配器拒绝错误字段并返回可恢复状态，不把原始长文本直接展示给用户。
5. 安全规则配置包不可用、过期或未命中：禁止具体药剂方案，只提供非化学措施、观察和复查。
6. 数据概览生成不可用：PC和移动端继续展示确定性图表与明细，不影响诊断和复查。

### 8.5 独立发布与验收

A0功能验证交互、数据和规则。A1功能使用固定模拟结果即可验收。A2功能通过离线评测和小流量灰度单独开放。

研发环境提供高置信、低置信、字段缺失、API超时、API不可用、响应结构异常和安全规则配置包不可用七类模拟数据。设计和前后端开发不得等待神农 API 新能力或模型优化完成。

### 8.6 神农API在意图识别中的职责

神农API用于理解自由文本、语音转写和复杂上下文，返回主意图、次意图和槽位候选。产品服务层负责协议校验、状态约束、风险覆盖、缺失字段、澄清和最终路由。API返回的意图置信度必须经过独立测试校准，不能直接当作真实概率。

如果神农API当前不支持稳定的结构化意图输出，研发先使用页面事件、规则和状态机上线P0流程，同时保留适配器字段和功能开关。该差距进入API能力缺口清单，不删除正常产品需求。

## 九 大模型能力详细设计

### 9.1 图片质量与视角识别

目标：识别模糊、曝光、遮挡、主体比例、作物存在性、病部可见性和视角类型。

输入：原始图片、尺寸、方向和可选设备信息。

输出：质量分、视角标签、问题原因和补拍动作。

业务规则：至少一张病部近景和一张全株或环境图才进入高证据路径。单图可以诊断，但降低诊断置信度。

### 9.2 作物 病部与症状识别

目标：识别作物候选、受影响部位、可见症状和影响范围。

输出：作物Top3、病部、症状标签、严重程度区间和用户确认问题。

限制：最高作物置信度低于校准阈值时，先让用户选择作物，不生成具体病害。

### 9.3 信息增益追问

目标：用最少问题区分主要候选。

输入：候选集合、已知症状、缺失字段和候选差异特征。

处理：估计每个问题对候选分布的影响，优先询问预期信息增益最高的问题。

输出：每轮最多两个可点击问题，并始终允许“不确定”。

### 9.4 多图融合与候选排序

目标：综合不同视角，避免对每张图分别给出冲突答案。

输入：图片特征、作物、病部、地区、季节、天气和症状。

输出：Top3候选、综合置信度、支持证据、冲突证据和缺失证据。

阈值必须通过真实验证集校准，不得直接使用经验值发布。

### 9.5 病斑定位与证据解释

目标：让用户知道系统依据了哪些可见特征。

输出：可开关标注层、关键症状、相似候选差异和不一致证据。

限制：病斑热区只作为解释辅助。标注不稳定时不展示。

### 9.6 神农 API 调用与结果结构化

目标：把神农 API 的图文诊断结果稳定转换为可被产品页面、规则校验和病例状态机使用的结构化字段。

输入：按接口规范处理的图片、作物、病部、地区、季节、生育期、结构化症状和用户描述。

处理：服务端完成鉴权、字段映射、异常处理和追踪；保留 API 明确返回的候选、置信度、证据和模型版本，缺失字段保持为空并标注原因。

输出：统一诊断协议、神农 API 请求追踪编号、响应时间、字段完整性和错误状态。

规则：不得使用自建知识库或RAG补齐缺失诊断字段，不得把神农 API 原始长文本直接作为完整结果页，也不得把API未返回的信息伪装成模型结论。

### 9.7 分层行动方案生成

目标：根据结果层级生成用户能执行的行动方案。

输入：神农 API 返回的候选与解释、风险、种植场景、天气、安全规则校验结果、固定方案模板和用户能力水平。

输出：现在做、未来三天观察、复查时间、调整条件和结束条件。

L2只允许候选共同适用的措施。L3优先隔离、清除明显受害部位、改善环境、限制扩散和标准化复拍。

### 9.8 通俗解释与分层阅读

目标：同一事实支持快速阅读和专业查看。

输出：一句话结论、行动版和依据版。三层内容必须引用同一结构化数据，不得出现病害名称、剂量和风险等级冲突。

### 9.9 疑难病例产品内闭环

目标：在不依赖外部人员的情况下完成低置信病例处理。

输入：候选结果、冲突证据、缺失证据、已执行措施和复查结果。

处理：选择补拍视角和结构化问题，计算候选共同措施，生成L2或L3方案，并设置下一次复查触发器。

输出：当前结果层级、安全行动、证据任务、复查时间和重新计算条件。

验收：任何低置信测试用例都不能以“请咨询专业人员”作为唯一结果。

### 9.10 连续复诊与效果总结

目标：判断症状变化并决定继续、调整或结束。

输入：首次与复查图片、实际措施、间隔时间、天气和用户反馈。

输出：改善、稳定、加重或无法比较，以及下一行动。

限制：角度、距离或光线差异较大时必须输出无法比较，并引导按首次轮廓重拍。

### 9.11 个人识别数据解读

目标：帮助用户理解自己的诊断记录和复查数据。

输入：确定性统计生成的诊断数量、作物分布、病虫害类别、结果层级和复查结果。

输出：简短数据概览、主要变化和对应病例入口。

限制：模型不能修改底层数字，不能从个人记录推断区域疫情，也不能把样本变化解释为风险预测。

### 9.12 反馈学习与模型监测

输入：用户纠错、实际执行、复查结果、投诉和离线标注结果。

处理：用户反馈进入待审核样本池，不能直接作为训练真值。内部质量团队维护金标准和错误分类。

输出：API版本或模型标识、错误分布、能力缺口、漂移预警、限流与超时趋势和接口协同建议。

内部质量审核只用于产品改进，不承接单个用户病例，也不形成面向用户的响应时限。

### 9.13 用户意图理解与槽位抽取

目标：从自然语言、语音转写、页面事件和病例上下文中识别主次意图并抽取槽位候选。

输入：用户文本、语音转写、当前页面、病例状态、上一轮候选、已确认槽位和风险规则命中结果。

输出：主意图、最多三个次意图、意图置信度、槽位候选、缺失槽位、候选意图和理由码。

限制：病虫害名称不能当作意图类别；模型不得覆盖用户已确认槽位，不得绕过高风险规则，不得凭自由文本直接触发具体用药发布。低意图置信进入按钮澄清，不创建外部人工服务单。

## 十 结构化输出协议

每次诊断调用返回结构化结果，不允许把模型长文本直接作为整页结果。核心字段包括：

1. 输入质量：是否可分析、问题原因、视角和补拍动作。
2. 作物信息：候选作物、病部、症状和用户确认状态。
3. 诊断候选：标识、名称、置信度、支持证据和冲突证据。
4. 结果层级：L1、L2或L3，以及层级原因。
5. 双置信度：诊断置信度、行动置信度和计算依据。
6. 风险等级：等级、影响范围和判定依据。
7. 行动方案：立即措施、观察项、复查时间、调整和结束条件。
8. 农药对象：只引用通过规则校验的结构化记录。
9. 安全规则：配置包版本、适用地区、有效期、命中状态和审核状态。
10. 行动状态：待执行、执行中、待复查和已结束。
11. 版本信息：神农 API 模型标识或接口版本、适配器版本、安全规则包版本、生成时间和追踪编号；API未返回模型标识时明确记为未知。

前端根据字段存在性展示组件。字段缺失时显示明确状态，不出现空白卡片或报错。

### 10.1 意图编排字段

诊断统一协议在原有结果字段之前增加意图编排对象，包含：协议版本、主意图、次意图、会话阶段、槽位和状态、缺失槽位、风险标签、下一动作、业务路由、候选意图和追踪编号。

主意图与次意图必须引用已发布标签版本。槽位值记录原始值、规范值、来源、置信度和确认状态。意图对象与诊断对象分别版本化，避免将“系统理解用户要做什么”和“系统判断是什么病”混为一个结果。

## 十一 安全与合规

### 11.1 诊断安全

1. 图片不足、作物未知或候选差异过小时不得输出唯一确定病名。
2. 每个有效病例必须输出L1、L2或L3方案。
3. 未通过安全规则配置包校验的药剂、剂量、混配或安全间隔期不得展示。
4. 每条具体措施绑定适用条件、配置包版本和生成时间。
5. 高风险或疑似检疫性有害生物进入内置合规提示流程，同时给出当前隔离和控制措施。
6. 神农 API 输出经过结构、敏感内容和农业安全规则校验后才展示。

### 11.2 防止伪闭环

以下做法均视为未解决：只显示无法识别、只要求重新拍照、只给知识文章、只提供联系电话、只生成转交摘要、只让用户等待人工回复。

补拍和追问必须与临时行动方案同时出现。系统不能把收集更多信息当作唯一结果。

### 11.3 数据安全

1. 按最小必要原则采集图片、语音和位置。
2. 用户明确授权后才能使用数据进行训练或评测。
3. 用户之间数据严格隔离，数据分析、导出和分享默认不包含精确位置。
4. 访问凭证、手机号和精确坐标不得进入模型提示词和普通日志。
5. 用户删除后，前台立即不可见，后台按政策进入可审计删除流程。

### 11.4 发布与回滚

神农 API 适配器、安全规则配置包和客户端协议分别版本化并可独立回滚。每次发布记录联调结果、评测结果、灰度范围、异常阈值和回滚条件。客户端不因 API 接口切换或适配器回滚而重新发布。

### 12.1 核心产品指标

| 双端同步成功率 | 同一病例在PC和移动端状态一致的比例 | 不低于99.9% |

### 12.2 PC 数据分析指标

1. 数据分析页访问率和筛选使用率。
2. 图表指标与组成病例一致率，目标100%。
3. 图表下钻到病例明细的成功率，目标100%。
4. PC创建病例后在移动端继续操作的比例。
5. 移动端创建病例后在PC查看详情或数据分析的比例。
6. 统计查询P95响应时间和空状态正确率。

### 12.3 模型指标

1. 作物识别Top1和Top3准确率。
2. 病虫害识别Top1和Top3准确率，并按作物、地区、设备和光照分层。
3. 诊断置信度校准误差和错误高置信率。
4. 图片质量问题召回率和无关图片拦截率。
5. L2和L3分层合理率。
6. 神农 API 响应解析成功率、目标字段完整率、安全规则命中率和违规拦截率，其中已发布方案的农药规则违规率必须为零。
7. 复查变化判断的一致率和无法比较识别率。
8. P50、P95响应时间、超时率和单病例推理成本。

营销材料中的90%以上或93%以上准确率不能直接作为上线目标。算法团队需先明确评测集、样本分布、类别粒度和统计方法。

### 12.4 意图识别指标

意图识别单独报告主意图准确率、Macro F1、Top 2召回率、多意图召回率、槽位F1、高风险意图召回率、错路由率、澄清率、澄清成功率和无匹配率。不得用总体准确率掩盖用药、人畜暴露和检疫等低频高风险类别。

## 十三 独立升级路线

### 13.1 产品工程线

第一阶段完成统一账号与病例协议、移动端拍照主入口、PC上传入口、三视图引导、结构化问诊、病例状态、行动清单和复查提醒。使用当前模型适配器和模拟数据验收。

第二阶段完成双端诊断记录、作物档案、执行记录、复查同步、PC病害识别数据分析、用量计算和轻量内部运维后台。该阶段不以神农 API 新增能力或模型优化为前置条件。

第三阶段完成L1至L3分层解决、双置信度展示、深度诊断编排和产品内闭环指标。神农 API 字段不足时，前端按字段缺失规范展示，非模型部分由规则和模板先行完成，但不得伪造模型结果。

第四阶段完善账号权益、配额计量、渠道接入、运营分析和服务质量工具。独立客户管理端不在本路线内。

### 13.2 神农 API 能力增强线

第一阶段完成神农 API 接口清单、联调样例、基线评测集、置信度字段验证和错误分类。

第二阶段协调并接入图片质量、作物病部、多图候选和结构化证据能力。

第三阶段协调并接入信息增益追问、病斑定位、复诊比较和个人数据解读能力。

API能力增强线按独立功能开关发布。任一阶段延迟不能阻塞产品工程线。研发团队不承担神农基础模型微调和自建知识库建设，重点负责接口适配、产品编排、验证和故障治理。

### 13.3 用户意图能力路线

第一阶段完成页面事件映射、会话状态、P0标签、主次意图队列、槽位存储、高风险规则和澄清按钮。第二阶段使用脱敏日志校准标签粒度、阈值和混淆对，并验证神农API的结构化分类稳定性。第三阶段增强地区口语、语音转写、跨病例指代和复杂复合诉求。三个阶段均不依赖知识库或基础模型微调。

## 十四 发布验收标准

1. 移动端首页无需打开隐藏菜单即可进入拍照或相册。
2. PC首页能够直接上传图片开始诊断，并查看最近病例和待复查病例。
3. 所有病例自动生成可区分标题并跨端同步。
4. 每个有效病例生成L1、L2或L3方案。
5. 低置信结果同时包含当前行动和继续诊断路径，不出现外部人工转交。
6. 结果页同时展示诊断置信度和行动置信度。
7. 任何具体农药建议均通过已审核安全规则配置包和确定性校验引擎校验。
8. 用户可以记录执行并完成复查，PC能够看到对应状态。
9. PC数据分析的每个指标均可下钻到组成病例，统计结果与明细一致。
10. 弱网、超时、上传失败、神农 API 不可用、安全规则配置包不可用和权限拒绝均有可恢复状态。
11. 神农 API 不可用时仍可完成建档、结构化问诊、模板型L3方案、执行记录和复查。
12. 神农 API 接口升级或适配器回滚不需要修改客户端页面和病例状态机。
13. 所有关键图标具备可访问名称，隐藏面板不进入焦点顺序。
14. 用户数据隔离和账号权限测试通过，不发生跨账号数据访问。
15. 用户界面、流程和产品协议中不存在专家接力、农技转单或人工诊断服务单。
16. 首期用户产品中不存在风险地图、区域治理、防控任务下发或独立客户管理入口。

### 14.1 意图专项验收

1. “这是什么病，怎么治，打什么药”识别一个诊断主意图和方案、药剂两个次意图，并按依赖顺序完成。
2. 用户在待复查页面说“还是很多”进入无效或加重流程，不新建病例。
3. “不要打药”记录绿色防控偏好，不误判为具体用药。
4. “不是辣椒，是茄子”更新作物槽位并保留纠错记录。
5. “两亩地一桶水放多少”在缺少已校验产品和标签剂量时先补条件，不直接计算。
6. “药溅眼睛了”覆盖普通诊断路由，立即进入人身暴露安全响应。
7. 意图低置信时显示互斥任务按钮；诊断低置信时生成L2或L3方案，两者不混淆。
8. 神农API不可用时，页面事件、状态机、结构化表单、高风险规则和病例流程仍可使用。
9. PC创建的病例在移动端继续时，主次意图队列和已确认槽位保持一致。
10. 任一低置信病例都不生成农技人员、专家或外部人工转单。

## 十五 关键风险与待确认项

1. 识别范围存在50多种作物480余种病虫害和75种作物615种病虫害两类口径，需要统一能力清单。
2. 准确率存在90%以上和93%以上两类口径，需要独立测试和统计定义。
3. PC现有病害识别数据分析的数据源、指标定义和可复用接口需要研发确认。
4. PC与小程序现有账号和病例数据能否打通需要技术评估。
5. 用户是否愿意完成多视图拍摄和复查，需要通过田间可用性测试验证。
6. 安全规则配置包的数据来源说明、审核责任、更新频率和地区适用需要业务、农业审核和法务共同确认。
7. 神农大模型 API 的图片数量、候选与置信字段、病斑定位、会话机制、错误码、限流、计费、数据留存和版本通知机制仍需以正式接口文档和联调结果确认。
8. 若未来出现明确的机构多人管理、任务下发或验收报表需求，应作为独立产品阶段重新论证，不在双端适配版本中预埋复杂管理流程。
9. 当前没有真实对话日志，79项标签的频率、边界、P0范围和置信阈值需要通过脱敏日志验证。
10. 神农API能否稳定输出主次意图、槽位和意图置信度，需要正式接口文档和联调样例确认。
11. 语音转写错误、地区口语、否定和跨病例指代可能造成错路由，必须进入专项测试集。
12. 意图日志的脱敏范围、保存期限和质量审核权限需要安全与法务确认。

## 附录二 意图评测与数据要求

每个二级意图首轮准备10至20条经过人工审核的种子表达，覆盖口语、错别字、语音转写、否定、指代、省略和多意图。训练、验证和测试按用户或病例分组切分，避免同一病例的相似表达同时进入训练和测试。

重点混淆对包括文字诊断与结果解释、综合防治与药剂选择、重新诊断与复查比较、预防与当前治疗、复查无效与新症状、能力查询与作物覆盖查询。评测报告按用户类型、作物、输入渠道和风险等级分层展示。

意图日志只保存完成质量分析所需的页面、状态、预测、规则命中、澄清选择和最终路由。API凭证、完整手机号、精确坐标、未脱敏正文和无必要的原始图片地址不得进入普通分析日志。
