# 神农卫田双智能体原型设计说明

版本：V1.0　日期：2026 年 11 月 6 日　用途：移动端与 PC Web 原型绘制

## 1 产品决策

神农卫田的消费端首页只突出两个任务：**智能诊断**与**农业问答**。智能诊断是持续跟进一个作物问题的 Personal Agent；农业问答是自由提问的会话智能体。两者共用同一账号，但采用不同的会话对象和入口文案。

智能诊断沿用既有的取证、诊断、方案、执行和复查能力。变化发生在交互层：Agent 根据用户描述、图片、病例状态和安全规则自行选择下一步。用户只在需要补图、回答关键问题、确认敏感条件或记录实际行动时介入。农业问答沿用当前演示会话界面的形式，补齐新建对话和历史管理。

本说明供画原型使用，列出需要画的页面、状态、组件和跳转。它承接 V2.4 的业务边界：PC 与移动端使用同一诊断逻辑；PC 保留个人病害识别数据分析；模型能力调用中国农业大学神农大模型 API；当前不建设知识库；低置信病例在产品内形成当前行动与继续诊断路径。

### 1.1 用户要感受到什么

用户进入诊断后，只需说“我的番茄叶子长斑了”或上传照片。Agent 应主动完成能完成的检查，并明确告知何时需要用户帮助。用户不必理解“作物选择、病部选择、症状填写、候选比较、方案生成”等内部步骤。

用户进入问答后，可以直接提问，例如“水稻稻飞虱怎么防治”。问答不自动创建病例，也不强制进入诊断流程。

### 1.2 设计原则

1. 首页让用户在 5 秒内分清“解决我的作物问题”和“问一个农业问题”。
2. 智能诊断始终是一个有状态的病例会话。Agent 每一步都知道当前病例、已确认信息和待完成任务。
3. 一轮最多要求用户处理一个主要动作，必要时最多提出两个关键问题。
4. Agent 的工作过程可见，但只展示可验证的进度、证据摘要、决策说明和下一步，不展示未经核验的内部推断文字。
5. 诊断结果先给“现在做什么”，再给原因、证据和候选解释。
6. 问答保持轻量，不把普通提问强行变成病例。
7. 无论模型能力是否增强，上传、病例、状态、确定性计算、安全校验、执行记录和复查都能独立工作。

## 2 双模块与导航

### 2.1 信息架构

```text
神农卫田
├─ 首页
│  ├─ 智能诊断 进入或新建诊断病例
│  ├─ 农业问答 进入或新建问答会话
│  ├─ 待我复查
│  └─ 最近使用
├─ 智能诊断
│  ├─ Agent 诊断会话
│  ├─ 病例详情与诊断结果
│  ├─ 执行记录
│  ├─ 复查会话
│  └─ 病例列表
├─ 农业问答
│  ├─ 问答会话
│  └─ 问答历史
└─ 我的
   ├─ 作物档案与可选地块
   ├─ 账号及隐私
   └─ 个人识别概览
```

PC Web 使用相同的两个主模块，在“我的记录”下增加病害识别数据分析。PC 数据分析只统计本人病例及可追溯明细，不提供风险地图、区域治理或独立客户管理入口。

### 2.2 会话对象

| 对象 | 创建时机 | 保存内容 | 可否跨端继续 | 结束方式 |

| 问答会话 | 点击“新建问答” | 问题与回答、引用的已显示上下文 | 可以 | 停止提问或新建问答 |

## 3 首页原型

### 3.1 移动端 H01

首屏顺序如下：

```text
神农卫田                                      我的

需要我帮你做什么？

┌ 智能诊断 ──────────────────────────────┐
│ 拍照或描述作物问题，我会继续诊断并跟进复查   │
│ [开始诊断]                                 │
└─────────────────────────────────────────┘

┌ 农业问答 ──────────────────────────────┐
│ 想了解病虫害、防治或用药常识，直接问我       │
│ [开始提问]                                 │
└─────────────────────────────────────────┘

待我复查  [查看全部]
番茄叶片异常  明天复查  [继续]

最近使用
黄瓜叶片发黄  诊断中
水稻稻飞虱怎么防治  问答

底部：首页｜诊断｜问答｜记录
```

首屏不放大段品牌介绍，不用三个固定问题代替模块解释。首页的两个卡片面积和视觉权重接近，但“智能诊断”置于第一位。待复查只在有待处理病例时显示。最近使用必须标明“诊断”或“问答”，不统一命名为“新对话”。

页面上提供一个清晰的“＋新建”动作。点击后只有“新建诊断”和“新建问答”两个选项；在对应模块内直接显示该模块的专用新建按钮。

### 3.2 PC H01

PC 首屏采用双栏：左侧为两个主任务入口和最近使用，右侧为待复查与最近病例。用户可拖拽图片到“智能诊断”卡片开始新病例。页面顶部持续可见“新建诊断”和“新建问答”。病害识别数据分析放在侧边导航，不挤占首页主行动。

### 3.3 首页交互状态

| 状态 | 页面变化 | 用户动作 |
|---|---|---|
| 首次进入 | 两个入口及一句解释，暂无历史区 | 开始诊断或开始提问 |
| 有未完成病例 | “继续上次诊断”置于智能诊断卡片下方 | 继续原病例或新建诊断 |
| 有待复查病例 | 显示到期作物、时间和“开始复查” | 进入原病例复查 |
| 问答进行中 | 最近使用显示问题标题与“问答”标签 | 继续问答或新建问答 |
| 弱网 | 显示本地草稿与同步状态 | 继续编辑或重试同步 |

## 4 智能诊断 Personal Agent

### 4.1 D01 诊断会话起点

诊断页面保留对话框。页面标题是“新诊断”或自动生成的病例标题，例如“番茄叶片出现黑斑”。标题旁有病例状态。首屏给一句任务提示：“发一张照片，或直接说说作物哪里不对劲。”底部输入区同时提供拍照、相册、语音和文字，拍照为视觉主操作。

用户提交后，Agent 自动执行：识别任务、检查图片有效性、提取作物与病部、查看已确认病例信息、判断是否需要补证、调用神农 API、整理结果与行动。用户界面不出现“第一步选择作物、第二步选择症状”的流程向导。

### 4.2 D02 可见的 Agent 工作动态

用户明确希望看到 Agent 像 Codex 解决问题那样推进。原型应把工作动态设计为诊断会话中的一张**可展开进度卡**。卡片默认展示阶段和最新动作；展开后展示已完成的检查、使用的信息和下一步。完成诊断后，卡片保留在病例时间线中供复盘。

```text
正在帮你判断这株番茄的问题                         进行中

✓ 已收到 2 张照片
✓ 已确认作物：番茄；异常部位：叶片
◐ 正在比较可能原因
○ 等待检查用药与采收安全条件

[查看工作过程]
```

展开后的单条工作动态采用统一字段：

| 字段 | 展示内容示例 | 规则 |
|---|---|---|
| 当前任务 | “判断叶片黑斑原因并给出今天的处理建议” | 用户能改写任务 |
| 当前阶段 | 检查图片、整理症状、比较候选、生成行动、等待补充、复查 | 只显示当前有效阶段 |
| 已核查信息 | “两张照片清晰；叶片有褐色斑；作物由你确认为番茄” | 区分用户确认和图像推断 |
| 证据与限制 | “叶背不可见，暂时无法排除另一种原因” | 只展示可追溯证据或明确缺口 |
| 本次决定 | “先补拍叶背，再细分病害候选” | 解释为什么要求用户介入 |
| 下一步 | “请拍一张叶背近照”或“正在生成行动建议” | 与页面主按钮一致 |
| 状态与时间 | 进行中、已完成、受阻；完成时间 | 失败时不能伪装已完成 |

**工作动态的展示边界：**可以展示 Agent 做了什么、依据了哪些已确认信息、为何需要补证、何时停止；不展示模型原始长推断、未校验的病名链条或内部提示词。诊断候选和药剂结论必须进入正式结果卡并经过产品校验。工作动态不承担最终处方的角色。

工作动态还需支持四种视觉状态：运行中为动态进度；等待用户时出现一个明确按钮；完成时可折叠；受阻时说明原因与可恢复动作。不要用无限滚动的“正在思考……”占位。每条状态的文案应随真实事件更新，超过预期时间显示“仍在处理，已保存你的图片与描述”。

### 4.3 D03 Agent 请求用户介入

Agent 只在自己无法可靠推进时打断用户。请求卡固定为“原因 + 具体动作 + 可跳过影响”，并在输入区上方呈现。

```text
还差一张关键照片
现在只看得到叶片正面，叶背特征能帮助我区分两个候选。
[拍摄叶背] [从相册选择] [暂时跳过]
跳过后仍会给出当前可执行措施，但病名可能保持候选状态。
```

同一轮最多提出两个关键问题，优先用大按钮或可选项回答；始终保留“我不清楚”。Agent 已掌握或用户已确认的信息不重复询问。语音转写先展示文字供用户修改。

用户补图后，Agent 继续原病例，工作动态新增“已收到叶背照片，正在重新比较候选”。补图失败时保留原会话、已上传图片和已确认槽位。

### 4.4 D04 结果与行动

结果仍嵌在同一诊断会话，不强制跳出聊天去看一张独立报告页。结果卡首屏顺序：

1. 一句话主要判断和结果层级 L1、L2 或 L3。
2. “现在做什么”行动清单，最多先展示三项。
3. 诊断把握程度与行动把握程度，分别解释。
4. “为什么这样判断”折叠区，展示可见证据、冲突证据、缺失证据和相似候选。
5. 未来观察项、复查时间和“记录已执行”。

L1 可给经过校验的具体方案。L2 展示候选共同适用的措施；L3 展示基于症状风险的保守措施。L2、L3 都要说明当前可以做什么和怎样继续收敛，不能只给“无法确定”。任何具体药剂、剂量、混配或采收建议都要经独立安全规则和标签适用性校验；条件不足时改为补充条件或展示非化学措施。

### 4.5 D05 低置信继续诊断

工作动态写明不确定性来自哪里，例如“照片缺少叶背”或“两个候选在当前证据下难以区分”。结果卡同时保留**当前行动**与**继续诊断**两个区域。继续诊断可由 Agent 发起补拍、结构化追问、候选差异确认；用户也可随时发消息纠正作物、补充历史或重新拍摄。

用户回答后，Agent 生成新的结果版本，旧结果仍可展开查看。不能因补图或复查新建不相关病例。停止追问的条件是：证据足够、继续追问收益很低、用户选择跳过，或达到本轮问题上限。停止后仍输出当前层级的行动方案和复查计划。

### 4.6 D06 执行和复查

用户可以直接说“我今天摘掉了病叶”，Agent 识别为执行记录请求，显示确认卡后写入当前病例。复查可由用户说“三天后提醒我”，也可点行动卡中的“设置复查”。到期时点击提醒回到原病例，Agent 主动询问变化并提示按相近视角补拍。

复查结果分为改善、稳定、加重和无法比较。若前后图角度、距离或光照差异过大，明确说明“无法可靠比较”，指导重拍，不强行判断改善。若无效或加重，Agent 继续原病例的诊断与方案更新。用户确认问题解决后结束病例。

### 4.7 D07 病例列表

列表项显示自动标题、作物、缩略图、最近更新时间和状态。状态至少包括“诊断中”“已给方案”“待复查”“已结束”。顶部有常驻“＋新建诊断”。搜索和筛选以作物、时间和状态为主。不要把每条记录都命名为“新对话”。

## 5 农业问答智能体

### 5.1 Q01 和 Q02 页面

延续当前演示会话界面：欢迎语、三个可点击的示例问题、聊天消息和底部输入框。首页模块解释更简短，因此问答页可保留现有介绍，但第一屏仍应看到输入区。顶部显示“农业问答”和“＋新建问答”；历史侧栏只收录问答会话，标题由首个问题生成。

问答可以询问病虫害知识、防治原则、绿色防控、天气条件和产品能力。它不自动创建诊断病例。若用户上传作物病部图片并要求“看看我的作物怎么了”，显示轻量提示：“这类问题适合智能诊断。转入后我会保存照片并持续跟进。”按钮为“转入智能诊断”和“继续问答”。只有用户点转入才创建病例。

问答中同样可以展示简短的“正在整理回答”状态，但不需要诊断 Agent 的完整工作动态。除非进入具体病例，不能假装已经完成图像取证、标签校验或安全规则计算。

## 6 双端布局规范

### 6.1 移动端

移动端以单栏对话为主。工作动态默认折叠成一张不超过两行摘要的卡片，用户点开查看详细过程；需要用户介入时自动展开当前请求。底部固定输入区为“拍照｜相册｜语音｜文字”，键盘弹起后保持发送与上传可达。主要按钮点击区域不小于 44 × 44 逻辑像素。

诊断结果的“现在做什么”先于详细证据；长证据、候选差异和历史工作动态折叠。问答页继续使用相对纯粹的聊天布局。诊断与问答用清晰标题和不同的状态标签区分，不依赖颜色单独识别。

### 6.2 PC Web

PC 诊断页推荐左侧病例列表、中间对话与结果、右侧可展开工作动态和病例信息。右栏能够同屏展示已确认槽位、证据与下一步，用户可快速纠错；工作动态不能遮住主对话。PC 问答页保留当前会话布局，仅优化新建入口和历史命名。个人病害识别数据分析从本人病例进入，可下钻到对应诊断会话。

| 元素 | 移动端 | PC Web |
|---|---|---|
| 工作动态 | 对话内折叠卡 | 对话内摘要加右侧详情栏 |
| 输入主方式 | 拍照、语音、相册 | 拖拽图片、文件选择、键盘 |
| 补证操作 | 大按钮一次处理一项 | 图片与已确认信息同屏查看 |
| 结果呈现 | 一屏结论和行动，详情折叠 | 结果、证据和候选可并列 |
| 记录 | 病例列表和简要个人概览 | 病例列表加个人识别数据分析 |

## 7 Agent 推进规则

### 7.1 状态与控制

病例状态为：空闲、收集信息、诊断中、结果已生成、方案已形成、措施已记录、待复查、已复查和已结束。Agent 可以建议下一步，实际状态由产品服务记录。每次状态变化需在会话时间线留下可读事件，供工作动态显示。

Agent 以“用户目标 → 已有信息 → 缺口 → 可用工具 → 下一动作”为内部编排顺序。页面只显示对应的工作动态摘要。明确按钮事件、状态和安全规则优先于模型意图猜测。用户纠正的信息优先于图片推断；纠错后重新计算，但不抹去旧版本。

### 7.2 什么时候自动推进

收到清晰图片和描述时，Agent 自动检查质量、抽取信息、调用诊断能力并生成结果。用户询问“这是什么病，怎么治，打什么药”时，Agent 将任务排成诊断、行动方案、药剂安全检查的顺序；前一步条件不足时说明卡点，不跳到药剂结论。用户在待复查病例说“还是很多”时，继续该病例的无效或加重流程。

### 7.3 什么时候等待用户

需要用户补图、确认作物或病部、补充关键时间与农事历史、确认药品标签或采收条件、确认删除和关闭病例时，Agent 暂停并给明确按钮。等待期间工作动态显示“等待你补充叶背照片”等具体任务，不显示空泛的“思考中”。

### 7.4 什么时候说明困难

当图片模糊、目标混杂、候选冲突、神农 API 超时、规则配置不可用或前后照片不可比时，Agent 应说清：目前完成了什么、卡在哪里、用户能做什么、当前可执行的安全措施。失败路径仍保留病例草稿、已确认信息与上传记录；不能伪造诊断完成，也不能把用户引向外部人工转单。

## 8 关键场景脚本

以下脚本可直接拆成画板。每个脚本建议分别画移动端关键帧，PC 端复用同一状态并调整布局。

### 8.1 正常诊断

1. 用户在 H01 点“开始诊断”，进入 D01；点击拍照并说“番茄叶子上有黑斑”。
2. D02 显示“已收到照片、正在检查清晰度、已识别疑似番茄叶片”。作物未确认时显示可点的“确认番茄”。
3. 若证据足够，Agent 自动进入比较候选。工作动态更新为“已比较两个常见原因，正在整理今天的行动”。
4. D04 出现结果卡，首屏是当前判断与三项行动。用户点“为什么这样判断”查看证据。
5. 用户说“我今天摘掉了病叶”，D06 出现执行确认卡，保存后给复查建议。

### 8.2 补图与低置信

1. 用户上传只有叶片正面的图片。D02 显示“已收到正面照片，叶背信息缺失”。
2. D03 出现“拍摄叶背”请求，说明补拍原因，并提供“暂时跳过”。
3. 用户跳过，D05 给 L2 或 L3 当前行动方案，明确病名仍不确定。
4. 用户稍后补图，Agent 继续原病例并生成结果版本 2；工作动态显示新证据和判断变化。

### 8.3 多意图与安全用药

1. 用户说“这是什么病，怎么治，两亩地打一桶水放多少药”。
2. D02 显示任务拆解：先判断作物问题，再形成行动方案，最后检查药剂与用量条件。
3. 诊断结果可生成当前安全行动。由于药品、标签剂量和桶容积缺失，Agent 暂停具体用量计算。
4. D03 请求用户提供药品标签照片或明确字段。若安全规则包不可用，X02 明确阻断具体药剂建议，保留非化学措施。

### 8.4 模型超时与恢复

1. 用户上传两张图片。D02 显示“图片已保存，正在诊断”。
2. 神农 API 超时后，X01 显示“本次诊断暂未完成；你的图片和描述已保存”。
3. 提供“重试诊断”“补充症状”“稍后继续”三个动作。重试不创建新病例。
4. API 恢复后，Agent 从原状态继续，并在工作动态标记先前受阻和恢复时间。

### 8.5 问答转诊断

1. 用户进入 Q01 提问“黄瓜霜霉病怎么防治”，得到普通问答。
2. 随后上传自己地里的叶片照片并说“我的这株是不是它”。
3. Q02 显示转入建议。用户点“转入智能诊断”后新建病例，照片与本轮问题带入 D01。
4. 原问答记录仍留在问答历史，新病例单独进入病例列表。

## 10 视觉与交互要求

### 10.1 设计气质

消费端应简洁、可信、亲近田间使用场景。建议以干净的浅色背景和深绿色作为功能色，图片与行动信息优先于大面积插画。品牌人物图可以在空白态出现，但不占据诊断会话的主要空间。结果层级与风险状态必须配文字，不只靠颜色表达。

### 10.2 对话消息类型

原型至少画出普通文字、用户图片、Agent 工作动态、补图请求、快捷回答、诊断结果、行动清单、执行确认、复查提醒、故障恢复和安全阻断十一种消息类型。它们应共享会话时间线，但卡片边界、按钮位置和状态视觉清楚区分。

### 10.3 新建与历史

“＋新建诊断”在诊断页与病例列表都可见；“＋新建问答”在问答页与问答历史都可见。新建前若当前输入未提交，提示保存草稿或放弃；已保存病例不需再次确认。历史侧栏中的诊断和问答分组清晰，不出现两个不可区分的“新对话”。

### 10.4 工作动态的交互细节

工作动态卡默认折叠、可展开、可回看。新增动态时只滚动到最新相关事件，不强制把用户从正在阅读的结果拉走。相同的处理中提示不重复刷屏。展开状态下，用户可点“更正这项信息”修改作物、病部或症状；更正会触发结果更新和版本记录。

## 11 原型验收清单

画完原型后逐项检查：

- [ ] 首页首屏明确区分智能诊断和农业问答，两个入口各自一句话说清用途。
- [ ] 首页、诊断页和问答页都有可发现的新建入口。
- [ ] 用户进入诊断后能直接拍照或描述，不必先经过多个选择页。
- [ ] 诊断会话包含可展开工作动态，能看出 Agent 当前任务、已完成检查、证据缺口与下一步。
- [ ] 工作动态的“等待用户”“进行中”“已完成”“受阻”状态都有对应画板。
- [ ] Agent 请求补图时说明原因、给具体拍法和跳过后的影响。
- [ ] 诊断结果首屏给当前行动，证据和候选可展开查看。
- [ ] L2、L3 低置信状态仍给行动和继续诊断路径。
- [ ] 用药安全条件不足时，没有可执行剂量或混配建议。
- [ ] 用户补图、纠错和复查后继续同一病例，结果版本可回看。
- [ ] 问答会话保持轻量，转诊断必须经过用户确认。
- [ ] PC 和移动端的同一病例状态、标题、结果与行动一致。
- [ ] 模型超时、上传失败和弱网场景均保留草稿并提供恢复动作。
- [ ] PC 病害识别数据分析能下钻到本人病例，不出现风险地图或管理端流程。
- [ ] 产品界面中没有农技人员转单、专家接力或人工诊断服务单。

## 12 绘制顺序与交付建议

先画移动端 H01、D01、D02、D03、D04、D05、D06、Q01 和 Q02，验证双模块与 Agent 主动推进的主路径。第二轮补 X01、X02、D07 和五条关键脚本。最后画 PC 适配与 P01 数据分析。这样可以先验证“轻量化”是否成立，再完善所有边界状态。

建议交付的原型包含：页面总览、移动端关键画板、PC 关键画板、每个按钮的跳转线、四态工作动态组件、诊断和问答各一条可点击完整流程。若原型工具支持变量，病例状态、图片数量、Agent 阶段、结果层级和是否需要用户补充应做成组件变量，减少大量重复画板。

## 13 待研发联调确认

**神农 API 评估调用额度不足（当前待确认项）。**目前可用调用次数过少，尚不足以运行既定的约 200—300 条评估集及多轮病例测试。需与接口提供方确认可用总额度、调用频率、图片与多轮请求的计费或扣次方式、测试环境和增额方式，并据此确定正式评估计划。在额度满足之前，只能进行少量接口字段与主流程联调；不得以该小样本推断病虫害识别准确率、端到端任务完成率或是否需要接入通用模型。原型及非模型功能可继续推进，完整模型评估列为上线前待完成项。

神农 API 是否直接返回结构化候选、图片质量、病部、置信度和意图字段，仍需以正式接口和联调样例确认。原型可以展示这些目标状态，但首期实现须区分“API 已有字段”和“产品通过规则或用户确认得到的字段”。工作动态必须由真实页面事件、接口返回和状态变更驱动，不能用固定计时动画假装完成真实检查。

具体药剂、剂量、混配和采收安全信息的来源、适用地区及规则版本需由业务与农业审核确认。原型只需明确校验入口、阻断状态和用户补充方式，不预填未经审核的处方。
